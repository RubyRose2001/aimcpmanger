## 6. 实现顺序

各步骤按依赖顺序推进，不跳步。

### 第一步：冻结接入条件与验证关键能力

**做什么：**

- 建立 OA 接口冻结清单，记录版本、补丁、模块、授权和特殊能力。
- 准备两个不同权限的测试账号。
- 验证公司固定信息与人员动态字段如何形成真实执行身份。
- 验证 WorkBuddy 的协议兼容、可信交互和人工来源证明。
- 明确测试环境、测试对象及允许产生的业务变化。

**验收标准：**

- OA 鉴权、身份及权限验证有真实证据。
- 每个接口具备明确范围和验证状态。
- 可信确认形成“通过”或“受阻及原因”的结论。

非查询受阻时，可以继续查询阶段建设，但不能把该能力记为通过。

### 第二步：建立工程、数据库和权限基础

**做什么：**

- 建立指定技术栈、迁移和本机管理员初始化流程。
- 实现后台账号、会话、角色、秘密管理及统一 API 层。
- 补齐 `UI_RULES.md` 和桌面、移动验收视口。
- 建立测试和部署基础。

**验收标准：**

- 登录、会话失效、改密、停用及越权测试通过。
- 密码和业务秘密不以明文进入数据库、日志或响应。
- 数据约束及迁移在测试环境验证通过。
- UI 规则已确认，方可开始具体样式实现。

### 第三步：完成人员、系统、配置与发布

**做什么：**

- 实现员工、系统绑定、固定秘密和动态字段维护。
- 实现接口配置、分类、映射、配置校验、草稿与发布。
- 实现受控调试授权。
- 实现编辑冲突、绑定复核及版本失效规则。

**验收标准：**

- 不同员工、不同系统的凭据不串用。
- 实施人员无法绕过工具授权或发布权限。
- 未批准的草稿不能直接触发真实业务调用。
- 系统字段变化后，不兼容绑定被阻止调用。
- 保存冲突不会覆盖其他人的修改。

### 第四步：完成 MCP 查询链路

**做什么：**

- 实现 MCP 连接、工具发现、逐人工具授权及实时校验。
- 完成查询执行、错误映射和调用日志。
- 验证代理链路、分页及运行保护。

**验收标准：**

- WorkBuddy 能发现并调用获授权查询工具。
- 两个不同权限 OA 账号的结果与 OA 一致。
- 未授权工具不可见且不可直接调用。
- 撤权、停用、吊销后，下一次调用被拒绝。
- 查询失败不自动重试。

### 第五步：完成非查询人工确认与执行控制

**前置条件：可信确认能力已验证通过。**

**做什么：**

- 实现预览、可信确认适配、验证码校验及状态机。
- 实现原子领取、固定执行快照及未知结果核查。
- 将非查询调试纳入相同流程。

**验收标准：**

- 模型不能获得或代填验证码。
- 后端能验证真实确认来源。
- 过期、改参、版本变化、撤权、错误码及复用均不能执行。
- **同一确认记录 50 次并发提交，最多发起一次业务请求。**
- 断线、领取后崩溃、响应丢失均不会自动重放。
- 核查接口不能执行业务或自动重试。

若前置条件仍受阻，停留在查询阶段，不以替代确认方式宣称完成。

### 第六步：完成接口覆盖、性能与业务验收

**做什么：**

- 逐项验证冻结范围内接口，包括特殊请求形式。
- 在明确部署规格、数据量和负载下压测。
- 验证日志清理、密钥轮换及隔离恢复。
- 完成真实业务验收和交付材料。

**验收标准：**

- 冻结清单内接口逐项通过；仅配置完成或受阻不计入通过。
- 行、语句、函数、分支覆盖率分别 **≥80%**。
- 所有关键权限、安全、确认、异常和恢复用例通过。
- 桌面、移动页面使用各自固定视口截图核对；新页面先确认设计基准。
- 正式容量、延迟和超时指标根据压测冻结。
- 业务负责人核对真实 OA 身份、权限及结果。

实施过程继续遵循：TypeScript 严格模式、禁用 `any`、函数式组件与 Hooks、规定命名方式、每个文件不超过 200 行、组件不直接请求网络；依赖评估后采用，代码改动配套测试，并按项目规范创建中文 Git commit。
