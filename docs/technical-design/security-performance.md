## 5. 安全与性能

### 5.1 权限控制

| 能力 | 企业管理员 | 实施／运维 | 普通员工 |
|---|---|---|---|
| 登录管理后台 | 是 | 是 | 否 |
| 创建、停用员工 | 是 | 否 | 否 |
| 维护人员系统绑定 | 是 | 是 | 否 |
| 录入、替换系统秘密 | 是 | 是 | 否 |
| 回读已保存秘密 | 否 | 否 | 否 |
| 维护接口草稿 | 是 | 是 | 否 |
| 发布、启停系统或工具 | 是 | 否 | 否 |
| 工具授权、撤权 | 是 | 否 | 否 |
| 员工 MCP 凭据签发与吊销 | 是 | 否 | 否 |
| 真实调试 | 获准范围内 | 获准范围内 | 不提供后台调试 |
| 查看日志 | 本公司日志 | 自身调试日志 | 无后台入口 |
| 调用 MCP 工具 | 需另有员工身份 | 需另有员工身份 | 仅获授权工具 |

单公司部署不建设共享 SaaS 公司管理台。我方维护服务器的权限与后台业务角色分别管理，不能宣称服务器控制者绝无获取运行时秘密的可能。

### 5.2 密码、凭据与秘密

- 初始管理员通过安装流程中的本机一次性初始化操作创建，不开放公共注册入口。
- 后台密码采用带随机盐的内存困难散列。
- 首版可使用 Node.js 异步 scrypt，基线参数为 `N=2^17、r=8、p=1`，随机盐至少 16 字节；明确配置足够内存上限，并限制登录散列并发。
- 保存算法、参数、盐和摘要，使用恒定时间比较。[OWASP 密码存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[Node.js Crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)

个人 MCP 凭据使用高熵随机值，建议不少于 32 个随机字节，数据库仅保存摘要。

业务秘密采用 AES-256-GCM 等带认证的加密方式。公司、资源及字段用途参与附加认证，防止密文被错误挪用。

加密主密钥与数据库、备份分开保管，维护密钥版本和轮换流程。验证码 HMAC 使用独立用途密钥。

人员脱敏开关仅作用于普通资料字段，默认关闭。密码、私钥、Token、Authorization 和验证码的保护不能关闭。

### 5.3 输入、网络与输出安全

- Prisma 查询保持参数化。
- 前端不直接接触业务系统秘密。
- 业务结果只返回已配置、获准的字段，过滤秘密及内部错误信息。
- 鉴权请求和鉴权响应不进入普通业务日志。
- 系统目标按批准的协议、域名、端口及网络范围访问，允许经批准的内网 OA。
- 每次解析检查实际地址，并使用已检查地址建立连接，保留正确 TLS 主机验证。
- 默认禁止重定向，阻止未批准的回环、链路本地及元数据服务地址。
- Agent 不能覆盖 Host、基础地址或鉴权头。
- 外部系统返回的文本按数据处理，不能改变平台权限或确认规则。

### 5.4 运行保护参数

以下为已确认的**初始配置**，正式性能结论必须经过指定环境压测。

| 参数 | 初始值 | 行为 |
|---|---:|---|
| 全平台在途业务请求 | 20 | 超额请求发送前拒绝 |
| 每系统在途请求 | 10 | 防止单个系统耗尽资源 |
| 每员工在途请求 | 2 | 防止单人占满容量 |
| 每员工调用频率 | 60 次／分钟 | 超额返回限流错误 |
| 默认执行超时 | 20 秒，可按接口配置 | 执行阶段使用统一时间预算，人工等待另计 |
| JSON 请求大小 | 1 MiB | 超限拒绝接收 |
| 业务响应大小 | 5 MiB | 流式累计限制；发送后的业务状态按证据判断 |
| 后台分页 | 默认 20，最多 100 | 避免一次加载全部数据 |
| 确认有效期 | 5 分钟 | 不维持一个请求等待五分钟 |
| 单记录验证码错误次数 | 5 次 | 达限失效 |
| 后台会话 | 空闲 30 分钟，最长 8 小时 | 到期重新登录 |

登录保护按账号及来源共同计数，采用递增等待，避免永久锁定造成拒绝服务。确认失败另设人员维度频控，具体阈值在可信交互联调后冻结。

达到容量上限的业务请求不进入延后执行队列。进程重启不能恢复或重放业务任务。

### 5.5 部署与十万条数据扩展

部署结构：

**HTTPS 反向代理 → 常驻 Next.js 服务 → PostgreSQL。**

数据库不直接对员工网络开放。MCP 流式路径单独配置代理缓冲及超时，并测试完整链路。[Next.js 自托管文档](https://nextjs.org/docs/app/guides/self-hosting)

首版不增加 Redis、消息队列或多实例。200–500 名员工是人员规模，不代表 500 个同时调用。

数据增长到十万条时按以下顺序处理：

1. 保证列表分页，日志使用稳定的时间与 ID 游标。
2. 只读取需要的字段，避免列表加载参数快照和大响应。
3. 根据真实查询建立复合索引，检查执行计划。
4. 分批清理到期日志及已结案确认记录。
5. 按实际瓶颈评估日志分区、数据库资源扩容。
6. 需要多实例时，再设计跨实例限流、并发控制和缓存一致性。

工具数量不设置套餐上限，但客户端工具发现、单页元数据大小和模型实际可处理规模必须验证。

### 5.6 日志、备份与恢复

普通调用及管理日志默认保留 30 天，可调整，到期实际清理。

已结束确认记录按配置周期清理；结果未知的记录保留至核查完成，再开始计算保留期。日志清理不能让旧确认重新获得执行资格。

数据库或必要审计无法写入时，拒绝发起新的业务请求，并记录受控运维故障信息。已领取或已发出的请求不能因审计故障重新执行。

备份规则：

- 每日加密备份，异机保存。
- 日志备份按事件到期时间管理，不额外延长日志保留期。
- 加密密钥单独保管并验证可恢复性。
- 每月在隔离环境进行恢复演练。
- 每日备份存在最近一次备份后的数据丢失窗口。

恢复流程：

1. 恢复环境默认关闭业务调用。
2. 统一失效旧后台会话、个人 MCP 凭据及待确认记录。
3. 对已领取而无法确认结果的记录保持未知状态。
4. 重新签发访问凭据。
5. 核查备份至故障期间的非查询操作。
6. 完成核查与恢复验证后再开放非查询执行。

“同一确认记录最多发起一次请求”不能扩展为跨数据丢失事故的端到端“恰好执行一次”承诺。

部署需要的主要配置包括：

| 配置 | 用途 |
|---|---|
| `DATABASE_URL` | 服务端数据库连接 |
| `APP_ORIGIN` | 后台可信来源与安全校验 |
| `SECRET_KEYRING_FILE` | 加密密钥文件位置 |
| `OTP_HMAC_KEY_FILE` | 确认码校验用途密钥位置 |
| 会话、并发、频率、大小及超时配置 | 使用本节初始值 |
| 可信确认适配配置 | 验证通过后配置；不能仅翻转开关就视为能力可用 |

任何密钥都不得进入前端公开环境变量。
