## 4. 边界与异常处理

### 4.1 空数据状态

| 场景 | 页面行为 |
|---|---|
| 尚无员工、系统或工具 | 展示明确空状态，并向有权限的人提供创建入口 |
| 筛选无结果 | 显示“没有符合条件的数据”，允许清空筛选 |
| 员工尚未绑定系统 | 显示待绑定提示，禁止相关工具调用 |
| 员工没有工具授权 | MCP 返回空工具列表 |
| 绑定字段不完整或待复核 | 显示缺失字段或复核原因，禁止调用 |
| 未发布或停用的工具 | 后台显示状态，不作为可执行工具开放 |

读取失败不能显示成“没有数据”。

### 4.2 网络失败、超时与重复提交

- 后台读取失败保留已有内容，显示错误和请求编号，支持手动刷新。
- 保存失败保留当前表单；秘密只保留在当前页面内存。
- 保存响应丢失时，根据管理操作记录查询结果，再决定是否重新提交。
- 服务端通过去重键、唯一约束和版本检查防止重复创建。
- 按钮禁用只作为交互措施，不能替代服务端防重复。
- 所有业务调用，包括查询，均不自动重试。
- 页面刷新、客户端重连和进程恢复不能触发业务重放。

请求体大小、调用频率和并发限制在业务请求发送前处理。业务响应大小只能在读取过程中检查；超过限制时停止读取，非查询的结果状态按实际证据判断。

### 4.3 多人修改与版本冲突

保存时携带 `revision`，服务端执行条件更新：

- 版本一致：保存并递增版本。
- 版本不一致：返回 `409`。
- 前端保留当前编辑内容，允许查看最新版后调整。
- 冲突响应只说明秘密字段是否变化，不返回秘密原文。

发布必须同时验证草稿版本和当前发布版本。管理员审核后草稿被修改，旧发布请求必须失败。

系统配置、业务凭据、人员绑定发生影响执行的变化时：

1. 更新对应版本或修订号。
2. 失效相关鉴权缓存。
3. 阻止旧待确认记录执行。
4. 必要时将人员绑定标记为待复核。

已领取执行的请求使用固定快照，不能被后续编辑改写。

### 4.4 非查询操作的确认与执行

确认状态：

**`PENDING → CLAIMED → SUCCEEDED / FAILED / UNKNOWN`**

`PENDING` 还可以进入：

- `EXPIRED`：超过五分钟。
- `CANCELLED`：用户或有权限的管理操作取消。
- `ATTEMPT_LIMIT`：累计五次验证码错误。
- `INVALIDATED`：权限、配置、绑定等变化使确认失效。

执行流程：

1. 保存业务参数、目标系统、执行人员和相关版本。
2. 向用户展示实际业务操作预览，秘密字段保持保护。
3. 后端生成确认码，仅通过受信任交互通道交付。
4. 用户亲自输入，客户端提交绑定本次记录的可信确认凭证。
5. 服务端检查来源、身份、权限、版本、有效期、验证码和一次性标识。
6. 在数据库事务内原子地将 `PENDING` 改为 `CLAIMED`。
7. 只有成功领取者能够发起业务请求。
8. 根据可靠证据记录成功、明确失败或结果未知。

验证码采用独立用途密钥进行 HMAC 校验存储。错误次数必须原子递增，不能因并发绕过次数限制。

领取事务捕获实际执行需要的配置、人员字段和凭据快照；事务提交后只使用该快照，秘密仅在服务端内存中短暂存在。数据库事务不跨越网络等待。

权限撤销、停用、发布与调用准入通过统一的短事务锁顺序协调：

- 变更先提交，后续调用或领取必须看到新状态。
- 调用已完成准入，属于已开始的执行；后续变更不能追回已经发出的 OA 请求。

领取后崩溃不得重新领取。恢复时无法确认结果的记录进入 `UNKNOWN`，不恢复执行。

### 4.5 可信交互的验证边界

可信确认凭证至少需要绑定：

- 公司和员工。
- 确认记录 ID。
- 业务参数摘要及相关配置版本。
- 服务端挑战、有效期和一次性标识。
- 可由服务端验证的可信来源。

**普通 MCP Bearer Token、页面隐藏、工具仅对 UI 可见，都不能独立证明是用户亲自确认。**

WorkBuddy 文档提到了 MCP Apps 内嵌能力，但不能据此推断其提供了本项目需要的交互隔离和签名机制。本设计将实际端点、签名算法、信任根和密钥登记流程列为验证后才能冻结的适配内容。[WorkBuddy 官方文档](https://open.workbuddy.cn/docs/buddy-app)

普通 MCP form elicitation 不用于收集能够授权交易的秘密，因此不使用普通表单或聊天文本承载本项目确认码。[MCP Elicitation 规范](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)

验证通过前禁止非查询执行，不擅自改成外部浏览器确认页。后台非查询调试同样遵守这一门禁。

### 4.6 结果未知的处理

`FAILED` 需要有明确失败或未执行的可靠证据。不能仅根据 HTTP 状态码、超时或列表暂未出现记录作判断。

对于 `UNKNOWN`：

1. 保留原记录及必要核查依据。
2. 使用获授权查询或 OA 审计核查对象、操作时间和业务流水。
3. 由管理员记录业务负责人确认的证据和结论。
4. 确认已执行，更新为成功或已执行的核查结论，不再提交。
5. 明确未执行，更新为明确失败；后续需要操作时重新预览、重新人工确认。
6. 仍不确定则继续保持 `UNKNOWN`。

核查接口不能执行业务，也不能自动生成重试。旧确认记录过期或被清理后，其 ID 一律不可执行，不根据缺失记录重新创建执行任务。

### 4.7 用户输入异常

- 服务端验证类型、长度、范围、枚举、必填项及未知字段。
- 动态字段必须符合对应系统发布版本的定义。
- 工具输入不得携带可覆盖身份或系统配置的字段。
- 用户文本按纯文本及对应输出上下文处理，禁止直接渲染 HTML。
- 不为了展示脱敏而改变实际鉴权值。
- 首版通用配置以 JSON 接口为基础；文件、XML、特殊签名和异步接口需按冻结清单评估适配。
- 如实现文件能力，必须同时校验实际文件类型、大小、数量及存储权限；未实现能力明确标为受阻。
